# 0006: Upgrade to Node 26 (explicit choice, not the LTS line)

Date: 2026-10-02
Status: accepted

## Context

The project was pinned to Node 24 (`engines.node: ">=24"`, `node:24-alpine` in
both Dockerfiles) specifically because it was the Active LTS line at the time,
while Node 26 was still the non-LTS "Current" release (confirmed against
nodejs.org's own release index: `v24.21.0` LTS vs `v26.10.0` not-LTS as of
this date). The user asked explicitly to move to Node 26 regardless.

## Decision

`engines.node` → `>=26`, both Dockerfiles → `node:26-alpine`, `@types/node` →
`^26.6.4` in `apps/api` and `apps/web` (to match the new runtime). Checked
every other dependency across the monorepo against npm's `latest` tag first —
everything else was already pinned to the actual latest compatible version
(confirmed in prior sessions); `typescript` stays at `6.0.3` since
`typescript-eslint`'s peer range is still `<6.1.0` (re-checked, unchanged —
see ADR 0001).

Two real breakages found only by actually building and booting the images,
not by reading changelogs:

1. **Corepack is no longer bundled with Node 26.** `RUN corepack enable` alone
   now fails (`corepack: not found`). Fixed in both Dockerfiles:
   `RUN npm install -g corepack && corepack enable`.
2. **`apps/web/Dockerfile`'s `CMD ["pnpm", "start"]` forced a network fetch of
   pnpm itself at container _runtime_, on every cold start.** The `runtime`
   stage is a fresh `FROM base`, not derived from `deps`/`build`, so it never
   inherits the Corepack cache populated while installing/building — the
   first `pnpm start` had to download pnpm from the registry before the app
   would even begin booting. This was latent since the web Dockerfile was
   first written, unrelated to the Node 26 move; it just hadn't been exercised
   end-to-end (built _and run_) until now. Fixed by invoking the already-
   resolved binary directly instead: `CMD ["node_modules/.bin/next", "start", "--port", "3100"]`
   — `pnpm deploy --prod` already put `next` in `node_modules/.bin` during the
   build stage, so no package manager is needed at runtime at all.

Also found and fixed while rebuilding `apps/api/Dockerfile` for this: its
`deps` stage never copied `apps/web/package.json`, so `pnpm install
--frozen-lockfile` failed once the lockfile gained `apps/web` as a workspace
member (added after the API Dockerfile was last touched) — pnpm needs every
workspace member's `package.json` present to resolve the lockfile, even ones
a given image never builds or ships. Fixed the same way in reverse for
`apps/web/Dockerfile` (it was missing `apps/api` and `packages/domain`).

## Consequences

- Node 26 is not LTS. Its support window is shorter than 24's, and it will see
  more churn before its own eventual LTS promotion (if it gets one — only
  even-numbered releases do). This was a deliberate tradeoff on the user's
  explicit instruction, not a default we'd recommend for a production pin
  without that instruction.
- Revisit when Node's next even-numbered release goes Active LTS, the same
  way this plan already did once (ADR context above).
- Any future new Dockerfile in this repo should copy **every** workspace
  member's `package.json` in its `deps` stage, not just the ones it directly
  depends on — this is now the second time a missing one broke a build.
